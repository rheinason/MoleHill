# Panel UI Review — 2026-07-04

Scope: `src/MoleHill.Rhino/UI/` — look and feel, input behavior (debouncing, commit semantics,
units), and extensibility (how easily new cards get added over the project's life). Static review
against the `rhino-eto-ui` skill guidance; items marked **[verify in Rhino]** need a live session
to confirm.

## Verdict

The panel is in good architectural shape for a project that will keep growing cards. The three
pillars are right: a shared card shell (`MoleHillPanel.Cards.cs`), a reusable editor vocabulary
(`MoleHillPanel.Editors.cs`), and a schema-driven card builder (`MoleHillPanel.Schema.cs`) fed by
the type registry. Adding a modifier today is genuinely "one descriptor + one definition" with no
UI plumbing. The main risks are: (1) the schema only covers **modifiers** — Analysis is a
~1,000-line hand-written switch that will keep growing unless it gets the same treatment; (2) the
`ParameterKind` vocabulary is missing kinds (enum/choice, color, text) that existing cards already
need, which silently pushes new work back into bespoke code; (3) a handful of input-behavior
inconsistencies (culture parsing, mid-typing commits, uniform stepper increments) that will get
copied into every future card if not fixed at the primitive level now.

## 1. Look and feel

### Working well
- **Theme system** — `UiTheme.cs` is a single token table (surfaces / text / interaction) keyed off
  Rhino's command-prompt background luminance, so the panel tracks Rhino's theme rather than the
  OS theme. Theme switches rebuild the whole content tree via `RhinoApp.AppSettingsChanged`
  (`MoleHillPanel.cs:1140`), so static surfaces recolor too. This is the right shape — every new
  card that sticks to `UiTheme` tokens is automatically theme-correct.
- **Card anatomy is genuinely uniform** — chevron, drag handle, icon plate with accent tint, enable
  checkbox, two-line title block, status pills, action buttons. `CreateSharedCardShell` +
  `SharedCardShellOptions` means a new card type binds ~6 controls instead of copying a header.
  The pinned base-triangulate card reuses the same shell with different colors — good precedent.
- **Responsive layout** — the four width breakpoints collapsed into one bitmask
  (`GetResponsiveLayoutKey`, `MoleHillPanel.cs:1210`) with named predicate helpers is clean, and
  editors consistently branch on `UseStackedFormRows()`. Content only rebuilds when the key
  actually changes.
- **Tooltips everywhere** — `ApplyHelp` is applied to essentially every interactive control, and
  numeric editors fall back to `GetNumericHelp(label)` so no field ships without help text.

### Issues / suggestions
- **Button vocabulary is drifting.** There are six factories (`MakeButton`, `MakeToolbarButton`,
  `MakeIconButton`, `MakeCompactButton`, `MakeMiniButton`, `MakePillButton`) with per-call-site
  pixel widths (`width: 86`, `width: 60`, `width: 38`, `width: 28`…). Every new card author has to
  guess which factory and which width. Suggest collapsing to three roles (toolbar / card-action /
  inline-mini) with fixed sizing inside the factory, and letting text width drive the rest. The
  hard-coded pixel widths are also the most likely thing to clip under larger Windows font
  scaling. **[verify in Rhino at 125%/150% scaling]**
- **Magic layout numbers live as consts but only in the main file** (`PropertyLabelWidth = 84`,
  `NumericLabelWidth = 96`, stepper `Width = 100`, dropdown `Width = 160`, slider `Width = 140`
  inline in `Editors.cs`). The inline ones should move next to the named consts (or into
  `UiTheme`) so future editors don't fork the values.
- **Chevron/handle glyphs are text labels** (`"▶"/"▼"`), which render differently per font. Fine
  for now; if the icon set grows, `PanelIcons` already supports 16×16 PNGs for these.
- **Header click-to-collapse** (`Cards.cs:305`) sits on the same surface as the enable checkbox and
  action buttons. Eto buttons/checkboxes normally swallow their clicks, but if a click on the
  checkbox *also* toggles collapse it will feel glitchy. **[verify in Rhino]**

## 2. Debouncing & commit behavior

### Working well
- **The deferral mechanism is the standout piece.** `BeginControllerRefreshDeferral` /
  `EndControllerRefreshDeferral` (`MoleHillPanel.cs:1168`) is a proper ref-counted guard: while a
  slider scrub or live numeric edit is in flight, controller `StateChanged` refreshes queue up
  instead of tearing the card (and the user's focus/scroll) down mid-edit, then flush once on
  release. Paired with `deferDocumentSave` + `suppressImmediateUiRefresh` on `MutateModifier`,
  this is exactly the "debounce expensive rebuilds outside the control handler" guidance.
- **Commit guards prevent no-op rebuilds** — `TerrainCommitGuard.HasMeaningfulNumericChange` and
  the string-equality check in `BindCommittedText` mean focus-cycling through fields never
  schedules a rebuild.
- **Text commits on Enter/blur only** (`BindCommittedText`, `MoleHillPanel.cs:2236`), with
  `e.Handled = true` on Enter. Correct per guidance.
- **Controller-side debounce exists too** — `FinalDebounceMs = 500`, `LiveEditSaveDebounceMs = 400`
  in `TerrainController`, so the UI debounce isn't the only line of defense.

### Issues / suggestions
- **Numeric editors commit mid-typing.** `CreateNumericEditor` restarts a 0.25 s `UITimer` on every
  `ValueChanged` and commits when it elapses (`Editors.cs:187-230`). `NumericStepper.ValueChanged`
  fires per keystroke, so a user who types `1`, pauses a beat, then types `25` commits `1` first —
  and with Live update on, that schedules a real terrain rebuild on a garbage intermediate value.
  For non-`liveEdit` editors the debounce-while-typing buys little; commit on Enter/blur (like
  `BindCommittedText`) would match the skill guidance and kill the partial-value rebuilds. Keep
  the timer only for `liveEdit`/scrub cases. Related: Enter does not commit numeric steppers at
  all today (no `KeyDown` hook) — only blur or the timer does.
- **Debounce intervals are scattered magic numbers** — 0.25 s (numeric, tolerance), 0.12 s (slider,
  objects), 500 ms / 400 ms (controller). Worth one `UiTiming` (or `UiTheme`) constants block so
  future editors don't invent a fifth interval.
- **Stale-timer edge on card teardown.** Every editor creates a closure-captured `UITimer` that is
  never disposed. Normal flow is safe (Commit stops the timer before mutating), but if an
  *external* `RefreshUi` rebuilds the stack while an editor's timer is pending, the orphaned
  timer still fires 0.25 s later against a disposed control — reading `stepper.Value` on a dead
  control and possibly committing a stale value through the captured terrain/modifier ids.
  Wiring `UnLoad` on the editor control to `timer.Stop()` closes it cheaply. **[verify in Rhino;
  feedback memory says probe-style flakes get misread — confirm before treating as a bug]**
- **Full-stack rebuild resets scroll position.** `RebuildModifierLayout` (`MoleHillPanel.cs:1477`)
  clears and repopulates the whole stack; nothing captures/restores the tab `Scrollable`'s
  `ScrollPosition` (only the layer-picker popover manages scroll). The deferral hides this during
  live edits, but any commit on a long stack likely snaps the view back to top. If confirmed,
  capture `ScrollPosition` before rebuild and restore after layout. **[verify in Rhino]**

## 3. Units & input niceties

### Working well
- **Slope units are a model implementation** — four units (%, ‰, ratio, degrees) with values
  *converted, not reinterpreted* when the unit changes (`CreateSlopeUnitEditor`,
  `MoleHillPanel.cs:2714` converts `RangeLow/High` to the new unit in the same mutate), and unit
  suffixes injected into row labels (`Low %` / `High °`).
- **Unit-aware defaults at creation** — `ModifierTypeDescriptor.Create(unitSystem)` means a pad
  created in a feet document gets sensible feet defaults. Most plugins get this wrong.
- **The slider text parse is culture-hardened** — `TryParseSliderNumericValue` (`Editors.cs:607`)
  deliberately drops `AllowThousands` and dual-parses CurrentCulture → Invariant, with a comment
  explaining the de-DE `1.000` trap. Exactly right.
- **Inherit-when-blank optional numerics** (`CreateOptionalNumericEditor`) with the inherited value
  as greyed placeholder is a genuinely nice pattern — worth using more widely.
- **Slider soft/hard range with auto-expansion** — `ExpandSliderRange`/`NiceNumber` grows the range
  to a 1/2/5 nice number when a typed value exceeds it, instead of clamping the user's input.

### Issues / suggestions
- **Length/area/volume fields never say what unit they're in.** Labels read `"sq units"`,
  `"cu units"`, `"model units"` (`Analysis.cs:240`, `MoleHillPanel.cs:2402`). The doc knows —
  `doc.ModelUnitSystem` — and a small helper (`FormatLength/FormatArea/FormatVolume(doc, value)`)
  would turn `Cut: 1523.40 cu units` into `Cut: 1 523.4 m³`. For a terrain tool this is the
  single highest-value input nicety on the list.
- **Culture handling is inconsistent between editors.** `CreateOptionalNumericEditor` parses
  CurrentCulture-only and formats with CurrentCulture (`Editors.cs:286-299`), while the slider
  editor formats Invariant and dual-parses. A German-locale user typing `1.5` gets different
  results in the two field types. Extract one shared `TryParseUserNumber` + `FormatUserNumber`
  pair and use it in every editor.
- **Stepper increments are one-size-fits-all** — `Increment = 0.1` for every decimal field
  regardless of whether it's a 0–1 factor, an angle in degrees, or a 50-unit width
  (`Editors.cs:179`). `ParameterDescriptor` has no `Increment`/step field, so schemas can't fix
  it either. Add `Step` to the descriptor (defaulted from decimals) and thread it through.
- **No semantic unit on parameters.** A `ParameterUnit` enum on the descriptor
  (Length/Angle/Percent/Factor/Count) could drive suffix labels, default increments, decimal
  places, and doc-unit formatting all at once — one field on the schema instead of per-card
  conventions. This is the natural follow-on to the two items above and pays off on every future
  card and on the planned GH-component generation.

## 4. Extensibility — the "cards will keep being added" lens

### Working well
- **The modifier path is the target picture.** Registry `README.md`'s "Adding a modifier" is a
  three-step recipe: definition + descriptor (Kind, metadata, `Create`, build-stage shim,
  `Parameters` schema) and reflection wires serialization, menu, factory, build dispatch, and the
  card. `AppendBespokeModifierRows` (`Modifiers.cs:132`) is a clearly-labeled escape hatch for the
  three rows the schema can't express — the bespoke code is quarantined, not the default.
- **All four families (modifiers/objects/markers/analyses) already have registries** for chrome,
  factories, and JSON polymorphism — the discovery/serialization half of extensibility is done.
- **Editor primitives cover the common vocabulary** and every one of them handles both responsive
  layouts internally, so card authors never write breakpoint code.

### Gaps, in priority order
1. **Analysis bodies are the anti-pattern the schema was built to kill.**
   `CreateAnalysisBody` (`Analysis.cs:144`) is a ~1,000-line `switch` over ten analysis types,
   with the same source/range/palette/format/layer/color row patterns repeated per case.
   `AnalysisTypeDescriptor` has no `Parameters`. Every new analysis card grows this switch. The
   fix is mechanical: reuse `ParameterDescriptor` (or a thin analysis variant), port the schema
   builder, and keep bespoke rows (legends, summaries) behind an `AppendBespokeAnalysisRows`
   escape hatch exactly like modifiers. `MoleHillPanel.Analysis.cs` at 60 KB shrinks by more than
   half, and new analyses become descriptor-only.
2. **`ParameterKind` is missing kinds that existing cards already use**, which is what forces
   bodies back to bespoke: **Choice/Enum** (slope-unit and value-format dropdowns), **Color**
   (`CreateOptionalColorEditor`), **Text** (`CreateCommittedTextEditor` — prefix/suffix fields),
   and arguably **Summary/legend** as a read-only rich kind. Each missing kind is a small
   addition to `ParameterDescriptor` + one case in `BuildSchemaRow` (`Schema.cs:36`); adding them
   *before* the next batch of cards prevents new bespoke bodies from accreting.
3. **Object bodies are half-migrated** — `CreateScatterObjectBody` (`Objects.cs:202`) is fully
   hand-written. Same recipe as #1 once the missing kinds exist.
4. **Descriptor gaps for input behavior** — no `Step`, no semantic unit, no `liveEdit` flag for
   plain numbers (only sliders get `LiveScrub`). These belong on the schema so behavior tuning is
   data, not editor-code archaeology.
5. **Main-file gravity.** `MoleHillPanel.cs` is 142 KB and still holds the toolbar, settings card,
   refresh machinery, drag/drop maps, mutate wrappers, *and* the shared helper vocabulary. The
   partials pattern works — continue it: `MoleHillPanel.Toolbar.cs` and
   `MoleHillPanel.Helpers.cs` splits would keep the main file navigable as tabs are added. The
   per-family dictionaries (`_modifierCardMap`/`_analysisCardMap`/… ×4 each,
   `MoleHillPanel.cs:99-112`) would also collapse nicely into one `CardStackState` object per
   family, which is what a sixth card family will want anyway.

## 6. Responsive restructure — implementation plan (Blender modifier-panel model)

**Why Blender is the reference.** Blender's modifier panel solves exactly our problem and has
three transferable rules:

- **Rule 1 — properties never lay themselves out.** Every property row goes through one layout
  primitive (`use_property_split`): label left / widget right at a fixed ~40/60 split, and the
  *layout engine* — not the property — moves the label above the widget when the region is
  narrow. Our equivalent: one `PropertyRow` control replaces every `if (UseStackedFormRows())`
  fork in `Editors.cs`.
- **Rule 2 — headers never carry inline action buttons.** A Blender modifier header is:
  chevron · icon · name · enable toggles · **one ⋮ "extras" dropdown** (Apply/Duplicate/Copy/
  Delete live in the menu). Because the header has one flexible element (the name), it fits at
  *any* width — Blender needs no header breakpoints, and neither will we.
- **Rule 3 — declarative properties, generated layout.** The modifier declares inputs; draw code
  is generated. We already have this (`ParameterDescriptor` + `Schema.cs`) — which is why this
  whole restructure stays inside `Editors.cs`/`Cards.cs` and no card builder changes.

Current state being replaced: `GetResponsiveLayoutKey()` (`MoleHillPanel.cs:1210`) buckets panel
width against 4 pixel thresholds into a bitmask; every editor forks its tree on it; crossing a
threshold rebuilds the entire `Content` (scroll/focus lost, no hysteresis).

Execute the stages in order; each compiles, ships, and is verifiable on its own.

### Stage 1 — `UiMetrics.cs` (new file, ~1 hr)

Pixel constants assume the default font. Replace them with character-width units, like CSS `ch`.

```csharp
// src/MoleHill.Rhino/UI/UiMetrics.cs
internal static class UiMetrics
{
    private static float _ch = -1f;

    /// <summary>Average character width of the default UI font, in logical pixels.</summary>
    private static float Ch
    {
        get
        {
            if (_ch < 0f)
            {
                using var font = Eto.Drawing.SystemFonts.Default();
                _ch = font.MeasureString("0000000000").Width / 10f;
            }
            return _ch;
        }
    }

    /// <summary>Call when the app font/theme may have changed (OnAppSettingsChanged).</summary>
    public static void Invalidate() => _ch = -1f;

    public static int Chs(double n) => (int)Math.Ceiling(n * Ch);

    // Named tokens — the ONLY place row/field dimensions are defined.
    public static int LabelColumn  => Chs(13);  // replaces NumericLabelWidth = 96
    public static int ShortLabel   => Chs(11);  // replaces PropertyLabelWidth = 84
    public static int NumericField => Chs(12);  // replaces stepper Width = 100
    public static int DropDown     => Chs(20);  // replaces Width = 160
    public static int SliderMin    => Chs(16);  // replaces Width = 140
    public static int RowBreak     => Chs(42);  // when a PropertyRow stacks (Stage 2)
    public static int Hysteresis   => Chs(1);
}
```

Tasks:
1. Create the file. Call `UiMetrics.Invalidate()` at the top of `OnAppSettingsChanged`
   (`MoleHillPanel.cs:1140`).
2. Replace every use of `PropertyLabelWidth`, `NumericLabelWidth`, and the inline
   `Width = 100/140/160/88` in `Editors.cs` with the tokens above. Delete the two consts.
3. Do **not** touch the four breakpoint consts yet (Stage 4 deletes them).

Acceptance: build passes; panel looks unchanged at default font; set Windows text size to 150%
(or Rhino's UI font larger) → labels and fields widen instead of clipping.

### Stage 2 — `PropertyRow.cs` (new file, ~half day + mechanical conversions)

The Blender `use_property_split` equivalent: a container that owns the label/widget arrangement
and re-arranges **the same child controls** when its own width changes. Controls are built once —
their event handlers, timers, and captured commit state survive every re-layout.

```csharp
// src/MoleHill.Rhino/UI/PropertyRow.cs
/// <summary>
/// One property row: label + widget. Lays out horizontally (label column left) when wide,
/// stacks the label above the widget when narrow. Children are created once and re-parented
/// on mode change, so editor state, focus wiring, and timers are preserved.
/// </summary>
internal sealed class PropertyRow : Panel
{
    private readonly Control _label;
    private readonly Control _widget;
    private readonly bool _expandWidget;
    private bool? _stacked;               // null = not laid out yet

    public PropertyRow(Control label, Control widget, bool expandWidget = false)
    {
        _label = label;
        _widget = widget;
        _expandWidget = expandWidget;
        SizeChanged += (_, _) => Apply(Width);
    }

    private void Apply(int width)
    {
        if (width <= 0)
            return;

        // Hysteresis so a width sitting on the boundary doesn't oscillate.
        bool stacked = _stacked == true
            ? width < UiMetrics.RowBreak + UiMetrics.Hysteresis
            : width < UiMetrics.RowBreak - UiMetrics.Hysteresis;
        if (_stacked == stacked)
            return;                        // ← loop guard: only touch Content on a real change

        _stacked = stacked;
        SuspendLayout();
        Content = null;                    // detach children before re-parenting (Eto requires it)
        Content = stacked ? BuildStacked() : BuildSplit();
        ResumeLayout();
    }

    private Control BuildSplit() => new StackLayout
    {
        Orientation = Orientation.Horizontal,
        Spacing = 6,
        VerticalContentAlignment = VerticalAlignment.Center,
        Padding = new Padding(0, 3),
        Items =
        {
            new StackLayoutItem(SizedLabel(UiMetrics.LabelColumn)),
            new StackLayoutItem(_widget, expand: _expandWidget)
        }
    };

    private Control BuildStacked() => new StackLayout
    {
        Orientation = Orientation.Vertical,
        Spacing = 4,
        Padding = new Padding(0, 3),
        HorizontalContentAlignment = HorizontalAlignment.Stretch,
        Items = { SizedLabel(0), new StackLayoutItem(_widget, HorizontalAlignment.Stretch) }
    };

    private Control SizedLabel(int width) { _label.Width = width > 0 ? width : -1; return _label; }
}
```

Then convert the editors in `Editors.cs` one at a time — each conversion deletes an
`if (UseStackedFormRows())` fork and ends with:

```csharp
return new PropertyRow(CreateHelpLabel(label, help, 0), stepper);
```

Conversion order (simplest first, so problems surface early on easy cases):
1. `CreateCheckEditor`  2. `CreateReadOnlyValueRow`  3. `CreateDropDownEditor` /
   `CreateValueFormatEditor`  4. `CreateCommittedTextEditor` (`expandWidget: true`)
5. `CreateNumericEditor`  6. `CreateOptionalNumericEditor`  7. `CreateSliderNumericEditor`
   (widget = slider+textbox in a small horizontal stack; `expandWidget: true`)
8. `CreateSourceEditor` + `CreateOptionalColorEditor` (delete the `UseStackedSourceEditors`
   fork — the pills column is already vertical; only the title placement changes)

Pitfalls for the implementer:
- Never rebuild `_label`/`_widget` — only re-parent. If you find yourself re-wiring an event
  inside `PropertyRow`, stop; that state belongs to the editor.
- `Content = null` before reassigning, or Eto throws "control already has a parent".
- The `_stacked == stacked` early-out is the infinite-loop guard; don't remove it.
- Old bitmask editors and converted `PropertyRow` editors coexist fine during the transition.

Acceptance (in Rhino): drag the panel edge 250 → 600 px slowly. Converted rows restack
*individually and smoothly*; a numeric field mid-edit keeps its typed value and focus across a
restack; no oscillation when parked exactly at the boundary.

### Stage 5 — width polish (opportunistic, with Stage 8 of the table)

- Buttons: remove `width:` arguments from `MakeMiniButton`/`MakeIconButton` call sites; let text
  size them with `MinimumSize = new Size(UiMetrics.Chs(4), HeaderActionHeight)`.
- Inputs: prefer `expand: true` + `UiMetrics` minimums over fixed widths (mostly falls out of
  Stage 2's `expandWidget`).
- Optional Blender parity later (separate work, see section 3): unit suffixes in numeric fields
  ("2.50 m"), drag-to-scrub on row labels, sliders for all 0–1 factors.

**Risk register for the implementer:** (a) per-row `SizeChanged` reliability under Eto/WPF is
the one assumption to validate *first* — build `PropertyRow`, drop it into a scratch tab with
two rows, and resize before converting all editors; if events are unreliable, fall back to one
panel-level width listener that calls `Apply(width)` on registered rows (same `PropertyRow`
API, different trigger); (b) `Scrollable` content width — rows must measure against their given
width, which `ExpandContentWidth = true` (already set, `MoleHillPanel.cs:1066`) provides;
(c) don't convert `SculptToolbarForm` or the dialogs — they're fixed-size surfaces and out of
scope.
